# OpenKB 概述

OpenKB 是一个面向 AI Agent 和开发者的中央、版本化项目知识库。

它的职责是让项目知识易于一次编写、审核、版本控制，并通过 MCP 作为按作用域限定的上下文对外提供服务。在实践中，它是一个 AI 大脑：一个持久化场所，Agent 可以在这里记住决定了什么、尝试了什么、哪些规则重要以及下一步该做什么。

> 一次编写项目知识。审核它。版本化它。然后让 Agent 通过 MCP 检索合适的知识片段。

## 为什么需要 OpenKB

软件项目会积累 Agent 所需的各种知识：

- 架构说明
- 编码规则
- 实现规范
- 审核工作流
- 运维手册
- 可复用的 Prompt 和 Skill
- 决策与参考资料

没有中央单一事实来源，这些知识就会散落在聊天记录、生成的文件、编辑器规则、团队文档和本地笔记中。Agent 会忘记上一次会话中发生的事情，用户必须重复解释相同的上下文。

OpenKB 将规范知识保存在服务器数据库中，并通过 MCP 动态提供。静态生成的文件不是产品的核心焦点。

## 简要流程

```text
人类和 Agent 编写知识
          ↓
OpenKB 将其存储为版本化的 Markdown 知识条目
          ↓
人类审核提交的变更
          ↓
Agent 通过 MCP 检索特定作用域的上下文
          ↓
Agent 在学到持久经验时提出新的记忆提案
```

## 核心概念

| 概念                 | 说明                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------ |
| **知识 (Knowledge)** | 单个 Markdown 知识条目，例如规则、规范、工作流、手册、技能或参考资料。               |
| **版本 (Version)**   | 每当更新知识条目时创建的不可变快照。                                                 |
| **作用域 (Scope)**   | 说明知识条目在何时相关的元数据：可选的项目和路径模式。                               |
| **提案 (Proposal)**  | 在成为规范知识之前可被审核的知识变更建议（状态：`open` / `approved` / `rejected`）。 |
| **Agent**            | 已注册的客户端身份（名称 + 权限）。知识归属使用拥有该 MCP 令牌的人类。               |
| **用户 (User)**      | 控制台账号（`name`、`email`、`role`），可以拥有 MCP 令牌并审核提案。                 |

## 知识是规范的基本单元

每个 OpenKB 知识条目包含：

| 字段        | 用途                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| `slug`      | 全局唯一标识符，例如 `backend-architecture`。                                 |
| `title`     | 人类可读的标题。                                                              |
| `summary`   | 列表和检索结果中显示的简短说明。                                              |
| `type`      | 知识分类。                                                                    |
| `status`    | `active`（ Agent 可检索）或 `inactive`（对 Agent 隐藏；仍可在控制台中查看）。 |
| `content`   | 完整的 Markdown 内容。                                                        |
| `scope`     | 可选的项目和路径匹配提示。                                                    |
| `version`   | 当前版本号（整数）。                                                          |
| `createdBy` | 当前版本的作者（版本行上的 `created_by`）。                                   |

支持的知识类型：

- `context`, `rule`, `spec`, `workflow`, `runbook`, `decision`, `reference`, `prompt`, `skill`, `template`

## OpenKB 不再围绕“项目”为中心

OpenKB 目前使用全局唯一的知识 slug。它不会在项目表中存储由项目所有的知识条目。

这意味着：

- 知识条目是独立的规范内容
- slug 在 OpenKB 服务器全局唯一
- 主键是自增整数 ID
- Agent 按名称全局注册（仅用于权限判断；知识归属使用令牌拥有者）
- Agent 通过兼容 MCP 的客户端连接
- Web UI 是面向人类的审核与管理界面（知识、提案、Agent、用户、设置）

这意味着 OpenKB 不是一个通用的单项目 Wiki。它是一个规范知识服务器和 AI 记忆层。客户端自行决定通过 MCP 请求哪些上下文。

## 作用域控制相关性

作用域使 OpenKB 能够返回精简、相关的上下文，而不是把每一个知识条目都堆给 Agent。

知识条目的作用域可通过如下方式限定：

```json
{
    "projectSlug": "openkb",
    "pathPatterns": ["backend/src/api/**", "frontend/src/views/**"]
}
```

当客户端请求上下文时，它可以传递 `path`、`projectSlug` 和 `limit`。OpenKB 过滤掉未激活的知识条目，检查作用域，然后对更具体的匹配给予更高排序权重。当用户正在编辑 API 代码时，特定路径的 API 规则会优于宽泛的通用笔记。Agent 名称不会过滤检索结果。

## 标准工作流

### 1. 捕获知识

知识可以通过 MCP 工具或 Web UI 进入 OpenKB。

### 2. 存储为版本化知识

创建或更新知识会写入 `knowledge` 表（元数据和指针）和 `knowledge_versions` 表（不可变的 Markdown 快照）。每次更新都会创建一个新版本。

### 3. 审核 Agent 提出的变更

除非 Agent 拥有直接写入权限，否则不应静默重写团队知识。

1. Agent 发现缺失或过时的知识
2. Agent 创建提案
3. 人类在 Web UI 中审核提案
4. 批准操作将更改作为新的知识版本应用

### 4. 工作时检索上下文

人类和 Agent 可以通过搜索关键字、按 slug 获取或请求特定作用域的上下文来动态检索知识。

### 5. 记住持久发现

当 Agent 学到了应当在当前会话结束后保留的内容时，应当调用 `openkb_remember`。

## 架构与集成界面

```text
                    ┌──────────────┐
                    │    Web UI    │
                    │  (Vue SPA)   │
                    └──────┬───────┘
                           │
┌─────────┐    ┌───────────┴───────────┐    ┌──────────┐
│ Web UI  │◄──►│   OpenKB Server       │◄──►│  Agents  │
│ (人类)  │    │      (MCP)            │    │  (MCP)   │
└─────────┘    └───────────┬───────────┘    └──────────┘
                           │
                    ┌──────┴──────┐
                    │  数据库     │
                    │   SQLite    │
                    └─────────────┘
```

1. **MCP 服务器**：面向 Agent 的原生主接口，用于上下文、搜索、知识检索、提案和可信写入。
2. **Web UI**：人类浏览、知识导入/导出、提案审核（包括恢复）、Agent、用户、令牌和文档界面。

## 实际示例

团队在 OpenKB 中有两份文档：

1. `api-auth-rules`：作用域限定为 `backend/src/api/**` 的规则
2. `vue-style-guide`：作用域限定为 `frontend/src/**` 的规则

如果一个 Agent 正在编辑 `backend/src/api/app.ts`，它通过 `openkb_get_context` 工具请求上下文。OpenKB 返回与该项目和 API 路径匹配的有效知识条目。不需要返回不相关的前端样式笔记。

如果 Agent 学到令牌撤销有一条特别的规则，它应该通过 `openkb_remember` 工具提出新知识或更新提案。人类对其进行审核。如果获得批准，OpenKB 会创建一个新的规范知识版本。

## 设计原则

- **规范数据库**：OpenKB 知识是单一事实来源。
- **版本化知识**：每一次知识更新都会创建一个不可变的版本。
- **提案优先的工作流**：Agent 可以建议持久化知识，而不会静默重写团队文档。
- **感知作用域的检索**：Agent 应当接收到合适的上下文，而不是所有知识条目。
- **MCP 优先的访问**：Agent 应当动态查询知识，而不是依赖静态的本地文件。
- **自托管优先**：Docker Compose 和 SQLite 是推荐的部署路径。
